# 避障车验收答辩常见问题与参考回答

本文按老师可能追问的方向整理。回答时可以先讲设计思路，再指出代码位置。

## 1. 整体架构

### Q1：这个工程总体分成哪些模块？

**答：**  
顶层是 `obstacle_car_top`，负责把开发板真实 IO 和内部模块接起来。核心模块包括：

- `key_debounce`：按键同步、防抖、生成单周期按下脉冲。
- `tick_gen`：产生低速 tick enable，不产生新时钟。
- `obstacle_game_core`：游戏 FSM、障碍生成、车辆移动、碰撞、胜败判定。
- `sevenseg_scan`：把 6 列 3 层游戏画面映射到 6 位数码管。
- `hp_led_pwm`：剩余生命 LED 呼吸和扣血爆闪。
- `buzzer_player`：播放碰撞短音和背景/胜利/失败整首音乐。

**代码位置：**

- 顶层实例化：`obstacle_car_top.sv:96`、`obstacle_car_top.sv:109`、`obstacle_car_top.sv:149`、`obstacle_car_top.sv:170`、`obstacle_car_top.sv:186`、`obstacle_car_top.sv:203`
- 游戏核心端口：`obstacle_game_core.sv:21`

### Q2：为什么坚持单时钟设计，而不是给扫描、下落、蜂鸣器分别分频出新时钟？

**答：**  
FPGA 设计里推荐单时钟域，低速动作使用 tick enable 控制。这样可以避免多个派生时钟带来的跨时钟域问题，时序约束也更简单。

`tick_gen` 输出的是一个主时钟周期宽度的使能脉冲，不是新时钟。比如 `STEP_TICK_HZ=2` 时，每 0.5 秒拉高一次 `step_tick`，游戏核心在 `if (step_tick_i)` 中更新障碍。

**代码位置：**

- 单时钟设计说明：`tick_gen.sv:8`
- tick 生成逻辑：`tick_gen.sv:48`
- 顶层 tick 实例化：`obstacle_car_top.sv:109`
- 游戏核心单个 `always_ff @(posedge clk_i)`：`obstacle_game_core.sv:187`

## 2. 状态机与游戏流程

### Q3：游戏状态机有哪些状态？

**答：**  
有四个状态：

```systemverilog
ST_IDLE
ST_RUN
ST_WIN
ST_LOSE
```

- `IDLE`：初始状态，清空障碍，车在中间，等待任意键开始。
- `RUN`：正常游戏，车移动、障碍下落、碰撞扣血。
- `WIN`：胜利状态，播放胜利音乐，按任意键返回 IDLE。
- `LOSE`：失败状态，HP 为 0，显示撞毁效果，播放失败音乐，按任意键返回 IDLE。

**代码位置：**

- 状态定义：`obstacle_game_core.sv:62`
- IDLE 逻辑：`obstacle_game_core.sv:220`
- RUN 逻辑：`obstacle_game_core.sv:243`
- WIN 逻辑：`obstacle_game_core.sv:341`
- LOSE 逻辑：`obstacle_game_core.sv:355`

### Q4：为什么胜利/失败后不是音乐播完自动回 IDLE？

**答：**  
现在设计成结算界面保持，玩家按任意键确认后返回 IDLE。这样玩家能看到胜利/失败结果，不会因为音乐结束太快而错过结算状态。音乐播完只会让蜂鸣器静音，不改变状态。

**代码位置：**

- `melody_done_i` 不切状态，只保留界面：`obstacle_game_core.sv:346`、`obstacle_game_core.sv:361`
- 任意键返回 IDLE 并停止音乐：`obstacle_game_core.sv:349`、`obstacle_game_core.sv:364`

### Q5：`music_start_pending` / `music_stop_pending` 是干什么的？

**答：**  
它相当于一个打一拍的事件寄存器。状态机本拍决定“要播放哪首音乐”，下一拍统一输出 `music_start_o/music_song_o/music_loop_o`。这样把“状态决策”和“对外事件脉冲”分开。

它不是功能上绝对必须，直接写 `music_start_o` 也可以。但 pending 写法让输出路径更集中，`music_start_o` 与 `music_song_o/music_loop_o` 的同拍关系更容易检查。

**代码位置：**

- pending 寄存器定义：`obstacle_game_core.sv:78`
- pending 统一输出和清零：`obstacle_game_core.sv:208`
- 开始背景音乐：`obstacle_game_core.sv:235`
- 胜利/失败音乐：`obstacle_game_core.sv:326`
- 返回 IDLE 停止音乐：`obstacle_game_core.sv:349`、`obstacle_game_core.sv:364`

## 3. 障碍生成与安全路径

### Q6：障碍是怎么随机生成的？

**答：**  
使用 16 位 LFSR 产生伪随机数。每次生成新障碍行时，用 LFSR 的不同位异或得到 6 位障碍图案，并混入 `row_index`，避免每一行完全重复。

**代码位置：**

- LFSR 状态：`obstacle_game_core.sv:91`
- LFSR 反馈多项式：`obstacle_game_core.sv:95`
- 障碍行生成：`obstacle_game_core.sv:130`

### Q7：如何保证永远存在一条不掉生命的通关路径？

**答：**  
核心是隐藏维护一个安全列 `safe_col`。

每次生成新障碍行前，先根据当前安全列计算下一行安全列。这个安全列最多左移一格、右移一格或保持不动。因为玩家每个下落周期也最多移动一格，所以这条安全路径始终可达。

生成障碍时，会强制安全列为空：

```systemverilog
row_value[open_col] = 1'b0;
```

后面补障碍保证至少 3 个障碍时，也排除了安全列：

```systemverilog
col != int'(open_col)
```

所以每一行都有一列是给安全路径留出来的。

**代码位置：**

- `safe_col` 定义：`obstacle_game_core.sv:91`
- 安全列最多移动一格：`obstacle_game_core.sv:103`
- 强制安全列为空：`obstacle_game_core.sv:142`
- 补障碍时不填安全列：`obstacle_game_core.sv:151`
- 生成新行时使用安全列：`obstacle_game_core.sv:280`

### Q8：这个保证是不是意味着随便按也不会掉血？

**答：**  
不是。它保证的是“始终存在一条可达的安全路径”，不是玩家随便移动都安全。如果玩家主动开进底层障碍，仍然会判定碰撞扣生命。

实际游戏中，玩家需要观察数码管障碍，选择正确方向跟随安全路径。

**代码位置：**

- 碰撞检测：`obstacle_game_core.sv:293`
- 撞到后扣血并清除障碍：`obstacle_game_core.sv:297`

### Q9：如果没有障碍下降，车左右移动撞到当前底层障碍会不会扣血？

**答：**  
会。`next_bottom` 在每拍开始时默认等于当前 `row_bottom`。如果没有 `step_tick_i`，`next_bottom` 就还是当前底层障碍；如果玩家左右移动进了障碍列，`hit = next_bottom[next_car_col]` 会检测到碰撞。

如果有 `step_tick_i`，`next_bottom` 会更新成从中层掉下来的 `row_mid`，此时检测的是刚下落到底层的障碍。

**代码位置：**

- `next_bottom` 默认等于 `row_bottom`：`obstacle_game_core.sv:258`
- step 时 `row_mid -> bottom`：`obstacle_game_core.sv:280`
- 用移动后的列检测碰撞：`obstacle_game_core.sv:296`

## 4. 车辆移动与碰撞判定

### Q10：车移动、障碍下降、碰撞判断是不是同一个时钟？

**答：**  
是同一个主时钟 `clk_i`。区别是：

- 车移动由 `key_pressed_i` 使能。
- 障碍下降由 `step_tick_i` 使能。
- 碰撞判断在同一个 `always_ff` 中使用本拍计算出来的 `next_car_col` 和 `next_bottom`。

这属于单时钟 + 多使能信号设计。

**代码位置：**

- 顶层把同一 `fpga_clk_i` 接给所有模块：`obstacle_car_top.sv:151`
- 车辆移动：`obstacle_game_core.sv:267`
- 障碍下降：`obstacle_game_core.sv:277`
- 碰撞检测：`obstacle_game_core.sv:293`

### Q11：为什么碰撞用 `next_car_col`，不用旧的 `car_col_o`？

**答：**  
这样可以让玩家在障碍下降同一拍按键时立即生效。逻辑顺序是：

1. 先根据按键算出移动后的 `next_car_col`。
2. 再根据 `step_tick_i` 算出下落后的 `next_bottom`。
3. 最后用 `next_bottom[next_car_col]` 判断碰撞。

如果用旧的 `car_col_o`，玩家明明在同一拍按键躲开了，仍可能按旧位置判定撞车，体验不合理。

**代码位置：**

- 先算移动后位置：`obstacle_game_core.sv:267`
- 再判断碰撞：`obstacle_game_core.sv:293`

### Q12：为什么同时按左右键时不移动？

**答：**  
这是为了避免输入冲突。代码只在左键按下且右键没按下时左移，或右键按下且左键没按下时右移。两个方向同时按下，不满足任一分支，因此保持原列。

**代码位置：**

- 左右键互斥判断：`obstacle_game_core.sv:271`
- testbench 覆盖同时按键不移动：`tb_obstacle_car.sv:570`

## 5. 按键、防抖与时基

### Q13：为什么需要按键防抖？

**答：**  
机械按键按下/松开瞬间会抖动，如果直接使用原始输入，可能一次按键触发多次移动。`key_debounce` 先做两级同步，再要求输入保持新状态达到 `DEBOUNCE_MS` 才确认变化。

确认从未按下变为按下时，输出 `key_pressed_o` 单周期脉冲；松开不会触发游戏动作。

**代码位置：**

- 两级同步：`key_debounce.sv:53`
- 计数确认稳定：`key_debounce.sv:80`
- 只在确认按下时产生脉冲：`key_debounce.sv:92`
- testbench 验证一次按下只产生一个脉冲：`tb_obstacle_car.sv:384`

### Q14：`tick_gen` 输出的 tick 是不是时钟？

**答：**  
不是。`tick_o` 是一个主时钟周期宽度的使能脉冲。所有模块仍在 `posedge clk_i` 工作，只是在 `if (tick_o)` 条件中执行低速动作。

**代码位置：**

- 模块说明：`tick_gen.sv:8`
- tick 拉高一拍：`tick_gen.sv:52`

## 6. 数码管与 LED 显示

### Q15：数码管如何显示 6 列 3 层游戏画面？

**答：**  
每个数码管代表一列。每列只用 A/G/D 三个横段表示三层：

- A 段：上层障碍。
- G 段：中层障碍。
- D 段：底层障碍和车。

`sevenseg_scan` 使用动态扫描，每次只选中一位数码管，快速轮询后人眼看到 6 位同时显示。

**代码位置：**

- 显示映射说明：`sevenseg_scan.sv:8`

- A/G/D 段映射：`sevenseg_scan.sv:69`
- 低有效段码输出：`sevenseg_scan.sv:90`

### Q16：为什么 IDLE 状态也显示中间车位闪烁？

**答：**  
这是初始界面提示。IDLE 时障碍清空、车列保持在中间，通过 `blink_phase` 控制车位闪烁，提示玩家当前在初始等待状态，可以按任意键开始。

**代码位置：**

- IDLE 重置车到中间：`obstacle_game_core.sv:220`

### Q17：生命值 LED 如何显示？

**答：**  
`hp_count` 从 4 到 0 映射成 LED 掩码：

```text
4 -> 1111
3 -> 0111
2 -> 0011
1 -> 0001
0 -> 0000
```

剩余 LED 做呼吸灯。扣血时，被扣掉的 LED 会先爆闪一段时间，再保持熄灭。

**代码位置：**

- HP 到 LED 掩码：`hp_led_pwm.sv:35`

## 7. 蜂鸣器与音乐播放

### Q18：新版音乐为什么不用音符表，而用 PCM ROM？

**答：**  
音符表需要从 MP3 里提取主旋律，复杂歌曲容易跑调。新版直接把音频转换成 4kHz/4bit 单声道 PCM，保留原音频波形，再由 FPGA 播放采样，所以旋律不会被重新识别错。

**代码位置：**

- `buzzer_player` 模块说明：`buzzer_player.sv:8`
- PCM ROM 读取：`buzzer_player.sv:115`
- 转换脚本采样率和曲目：`tools/generate_buzzer_pcm.py:15`、`tools/generate_buzzer_pcm.py:18`

### Q19：`buzzer_pcm_rom.mem` 和 `buzzer_pcm_rom.svh` 分别是什么？

**答：**

- `buzzer_pcm_rom.mem`：真正的音乐数据，一行一个十六进制 byte。
- `buzzer_pcm_rom.svh`：记录每首歌在 ROM 中的起始、长度、结束位置，并提供 `pcm_song_start()` 和 `pcm_song_last()` 函数。

`.mem` 由 `$readmemh` 加载到 `pcm_rom`。Vivado 支持这种方式初始化 ROM。

**代码位置：**

- ROM 常量：`buzzer_pcm_rom.svh:7`
- 三首歌起止位置：`buzzer_pcm_rom.svh:11`
- 查起始/结束函数：`buzzer_pcm_rom.svh:23`
- `$readmemh` 加载：`buzzer_player.sv:117`

### Q20：为什么是 4kHz/4bit，而不是 8kHz/8bit？

**答：**  
主要是片上 BRAM 空间限制。三首整首音乐如果用 8kHz/8bit，大约 3.25MB，超过片上 BRAM。现在用 4kHz/4bit，三首合计约 813KB，能更容易放进 FPGA 片上 ROM。

牺牲的是音质，保留的是旋律和节奏。实际蜂鸣器输出会像低清电子玩具音，但不会像音符提取那样跑调。

**代码位置：**

- 采样率：`buzzer_pcm_rom.svh:7`
- 总采样数/字节数：`buzzer_pcm_rom.svh:8`
- Python 转换量化：`tools/generate_buzzer_pcm.py:61`
- 两个 4bit 采样打包 1 byte：`tools/generate_buzzer_pcm.py:84`

### Q21：Sigma-Delta 是什么？为什么要在 FPGA 里做？

**答：**  
蜂鸣器只有一个 `beep_o` 数字引脚，不能直接输出多 bit 模拟音频。Sigma-Delta 把 4bit 采样转换成高速 1bit 码流。1 的比例越高，等效平均电压越高，从而近似还原音频波形。

放在 FPGA 里做是为了省 ROM。如果提前离线生成 1bit 高速码流，数据量会比现在大很多，不适合把整首歌放进片上 ROM。

**代码位置：**

- 当前采样和累加器：`buzzer_player.sv:153`
- Sigma-Delta 更新：`buzzer_player.sv:285`
- `beep_o` 输出：`buzzer_player.sv:289`

### Q22：音量怎么调？

**答：**  
通过 `VOLUME_SHIFT` 调数字音量：

- `0`：接近满音量。
- `1`：约 50%，当前默认。
- `2`：约 25%。

它把 4bit 采样以 8 为中心缩小振幅，再加回 8。这样可以降低蜂鸣器刺耳程度。

**代码位置：**

- 参数定义：`buzzer_player.sv:22`
- 音量缩放函数：`buzzer_player.sv:130`

### Q23：普通碰撞短音会不会让背景音乐重头播放？

**答：**  
不会。如果碰撞发生在背景音乐期间，播放器进入 `MODE_COLLISION` 播短音，但不清除 `sample_index`。短音结束后，如果 `resume_song_after_collision=1`，回到 `MODE_SONG`，继续原来的采样位置。

**代码位置：**

- 背景音乐碰撞打断：`buzzer_player.sv:275`
- 碰撞短音结束后恢复：`buzzer_player.sv:250`
- testbench 验证续播而不是重启：`tb_obstacle_car.sv:477`

### Q24：胜利/失败音乐是完整播放吗？

**答：**  
是。`music_loop_o=0` 时播放一次，播到歌曲末尾后 `done_o` 拉高一拍并静音；状态机仍停在 WIN/LOSE，等待按键返回 IDLE。背景音乐 `music_loop_o=1`，播到末尾后回到开头循环。

**代码位置：**

- 胜利/失败启动时 `music_loop_pending=0`：`obstacle_game_core.sv:326`
- 背景启动时 `music_loop_pending=1`：`obstacle_game_core.sv:235`
- 曲末循环或 done：`buzzer_player.sv:297`

## 8. 资源与工程文件

### Q25：这块板子是不是存储资源很少？

**答：**  
板子外部存储不小，例如 SPI Flash / SD 卡，但最容易直接用 `$readmemh` 初始化的片上 BRAM 资源有限。整首音乐如果用高质量采样会很快超过片上 BRAM，所以当前选择 4kHz/4bit。

如果要明显提升音质，需要使用 SPI Flash、SD 卡或 DDR 做流式读取，但这会增加外部存储控制器和文件读取逻辑，超出当前课程设计重点。

**代码位置：**

- 当前 ROM 体量：`buzzer_pcm_rom.svh:8`
- `.mem` 作为 Vivado Memory File 加入工程：`Obstacle_Avoidance_Car_Project.xpr:136`

### Q26：为什么 `.mem` 文件要上传 GitHub？

**答：**  
`.mem` 是音乐 ROM 的实际数据，`buzzer_player` 依赖它初始化 `pcm_rom`。如果不上传，别人拉工程后能看到 RTL，但 ROM 没有内容，音乐无法正确播放。

可以不上传 `music/buzzer_generated/` 里的试听文件，因为它们可以由脚本重新生成。

**代码位置：**

- `$readmemh` 使用 `.mem`：`buzzer_player.sv:117`
- 生成 `.mem`：`tools/generate_buzzer_pcm.py:93`
- `.gitignore` 忽略生成预览：`.gitignore:84`

### Q28：如果老师问“这个能综合吗？”

**答：**  
代码风格上是可综合的：主体逻辑使用 `always_ff @(posedge clk_i)`，低速动作使用 enable，不产生派生时钟；ROM 使用 `$readmemh` 初始化数组，Vivado 支持推断初始化 ROM/BRAM。

需要注意的是音乐 ROM 体量较大，综合时资源占用会明显增加。如果综合资源压力太大，可以降低采样率、降低音乐长度，或改成外部 Flash/SD 流式播放。

**代码位置：**

- 单时钟设计：`obstacle_car_top.sv:13`
- PCM ROM 声明和初始化：`buzzer_player.sv:115`
- ROM 数据大小：`buzzer_pcm_rom.svh:8`

## 10. 一句话答辩总结

本设计采用单时钟域结构，使用 tick enable 控制低速游戏逻辑。游戏核心用 FSM 管理 IDLE/RUN/WIN/LOSE，通过 LFSR 生成障碍，并用 `safe_col` 保证始终存在可达安全路径。显示部分用数码管动态扫描呈现 6 列 3 层画面，LED 用 PWM 表示生命值。新版蜂鸣器不再使用音符表，而是把整首音乐离线转换为 4kHz/4bit PCM ROM，在 FPGA 内实时 Sigma-Delta 调制成 1bit `beep_o` 输出，从而保留原曲旋律并适配单引脚无源蜂鸣器。
