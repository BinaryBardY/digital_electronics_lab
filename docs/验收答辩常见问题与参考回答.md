# 避障车验收答辩常见问题与参考回答

本文按老师可能追问的方向整理。回答时可以先讲设计思路，再指出代码位置。

## 1. 整体架构

### Q1：这个工程总体分成哪些模块？

**答：**  
顶层是 `obstacle_car_top`，负责把开发板真实 IO 和内部模块接起来。核心模块包括：

- `key_debounce`：按键同步、防抖、生成单周期按下脉冲。
- `tick_gen`：产生低速 tick enable，不产生新时钟。
- `obstacle_game_core`：游戏 FSM、障碍生成、车辆移动、碰撞、胜败判定。
- `sevenseg_scan`：把 6 列 3 层游戏画面映射到 6 位数码管。
- `hp_led_pwm`：剩余生命 LED 呼吸和扣血爆闪。
- `buzzer_note_player`：播放碰撞短音和背景/胜利/失败蜂鸣器旋律。

**代码位置：**

- 顶层实例化：`obstacle_car_top.sv:96`、`obstacle_car_top.sv:109`、`obstacle_car_top.sv:149`、`obstacle_car_top.sv:170`、`obstacle_car_top.sv:186`、`obstacle_car_top.sv:203`
- 游戏核心端口：`obstacle_game_core.sv:21`

### Q2：为什么坚持单时钟设计，而不是给扫描、下落、蜂鸣器分别分频出新时钟？

**答：**  
FPGA 设计里推荐单时钟域，低速动作使用 tick enable 控制。这样可以避免多个派生时钟带来的跨时钟域问题，时序约束也更简单。

`tick_gen` 输出的是一个主时钟周期宽度的使能脉冲，不是新时钟。比如 `STEP_TICK_HZ=2` 时，每 0.5 秒拉高一次 `step_tick`，游戏核心在 `if (step_tick_i)` 中更新障碍。

**代码位置：**

- 单时钟设计说明：`tick_gen.sv:8`
- tick 生成逻辑：`tick_gen.sv:48`
- 顶层 tick 实例化：`obstacle_car_top.sv:109`
- 游戏核心单个 `always_ff @(posedge clk_i)`：`obstacle_game_core.sv:187`

## 2. 状态机与游戏流程

### Q3：游戏状态机有哪些状态？

**答：**  
有四个状态：

```systemverilog
ST_IDLE
ST_RUN
ST_WIN
ST_LOSE
```

- `IDLE`：初始状态，清空障碍，车在中间，等待任意键开始。
- `RUN`：正常游戏，车移动、障碍下落、碰撞扣血。
- `WIN`：胜利状态，播放胜利音乐，按任意键返回 IDLE。
- `LOSE`：失败状态，HP 为 0，显示撞毁效果，播放失败音乐，按任意键返回 IDLE。

**代码位置：**

- 状态定义：`obstacle_game_core.sv:62`
- IDLE 逻辑：`obstacle_game_core.sv:220`
- RUN 逻辑：`obstacle_game_core.sv:243`
- WIN 逻辑：`obstacle_game_core.sv:341`
- LOSE 逻辑：`obstacle_game_core.sv:355`

### Q4：为什么胜利/失败后不是音乐播完自动回 IDLE？

**答：**  
现在设计成结算界面保持，玩家按任意键确认后返回 IDLE。这样玩家能看到胜利/失败结果，不会因为音乐结束太快而错过结算状态。音乐播完只会让蜂鸣器静音，不改变状态。

**代码位置：**

- `melody_done_i` 不切状态，只保留界面：`obstacle_game_core.sv:346`、`obstacle_game_core.sv:361`
- 任意键返回 IDLE 并停止音乐：`obstacle_game_core.sv:349`、`obstacle_game_core.sv:364`

### Q5：`music_start_pending` / `music_stop_pending` 是干什么的？

**答：**  
它相当于一个打一拍的事件寄存器。状态机本拍决定“要播放哪首音乐”，下一拍统一输出 `music_start_o/music_song_o/music_loop_o`。这样把“状态决策”和“对外事件脉冲”分开。

它不是功能上绝对必须，直接写 `music_start_o` 也可以。但 pending 写法让输出路径更集中，`music_start_o` 与 `music_song_o/music_loop_o` 的同拍关系更容易检查。

**代码位置：**

- pending 寄存器定义：`obstacle_game_core.sv:78`
- pending 统一输出和清零：`obstacle_game_core.sv:208`
- 开始游戏时启动循环背景曲：`obstacle_game_core.sv:263`
- 胜利/失败音乐：`obstacle_game_core.sv:326`
- 返回 IDLE 停止音乐：`obstacle_game_core.sv:349`、`obstacle_game_core.sv:364`

## 3. 障碍生成与安全路径

### Q6：障碍是怎么随机生成的？

**答：**  
使用 16 位 LFSR 产生伪随机数。每次生成新障碍行时，用 LFSR 的不同位异或得到 6 位障碍图案，并混入 `row_index`，避免每一行完全重复。

**代码位置：**

- LFSR 状态：`obstacle_game_core.sv:91`
- LFSR 反馈多项式：`obstacle_game_core.sv:95`
- 障碍行生成：`obstacle_game_core.sv:130`

### Q7：如何保证永远存在一条不掉生命的通关路径？

**答：**  
核心是维护一个安全列 `safe_col`，并保证这一列不会生成障碍。

安全列不会每行乱跳，而是通过 `safe_hold_count` 保持 2 到 3 层后强制漂移。漂移时最多左移一格或右移一格，边界处自动向内回拐，不再允许长期保持不动。生成障碍时清空安全列本身；通道拐弯时还会把上一条安全列作为过渡列临时留空，这样玩家不会被旧底层障碍卡死，同时又必须跟着路线移动。

生成障碍时，会强制安全列和过渡列为空：

```systemverilog
row_value[open_col] = 1'b0;
row_value[support_col] = 1'b0;
```

障碍行现在从 `6'b111111` 开始，再清掉主安全列、过渡列和一个额外空位。额外空位优先选择上一行有障碍的列，减少连续几行同列刷新的观感：

```systemverilog
row_value[extra_gap_col] = 1'b0;
```

所以每一行都有安全列和过渡空间，同时障碍分布不会长期固定在同几列。这个掩码生成方式也比“计数、裁剪、补障碍”的组合逻辑短，更利于时序。

**代码位置：**

- `safe_col` / `safe_hold_count` 定义：`obstacle_game_core.sv:93`
- 安全列最多移动一格：`obstacle_game_core.sv:107`
- 过渡列选择：`obstacle_game_core.sv:124`
- 额外空位选择：`obstacle_game_core.sv:157`
- 掩码式障碍生成：`obstacle_game_core.sv:200`
- 生成新行时使用安全列：`obstacle_game_core.sv:354`

### Q8：这个保证是不是意味着随便按也不会掉血？

**答：**  
不是。它保证的是“始终存在一条可达的安全路径”，不是玩家随便移动都安全。如果玩家主动开进底层障碍，仍然会判定碰撞扣生命。

实际游戏中，玩家需要观察数码管障碍，选择正确方向跟随安全路径。

**代码位置：**

- 碰撞检测：`obstacle_game_core.sv:293`
- 撞到后扣血并清除障碍：`obstacle_game_core.sv:297`

### Q9：如果没有障碍下降，车左右移动撞到当前底层障碍会不会扣血？

**答：**  
会。`next_bottom` 在每拍开始时默认等于当前 `row_bottom`。如果没有 `step_tick_i`，`next_bottom` 就还是当前底层障碍；如果玩家左右移动进了障碍列，`hit = next_bottom[next_car_col]` 会检测到碰撞。

如果有 `step_tick_i`，`next_bottom` 会更新成从中层掉下来的 `row_mid`，此时检测的是刚下落到底层的障碍。

**代码位置：**

- `next_bottom` 默认等于 `row_bottom`：`obstacle_game_core.sv:258`
- step 时 `row_mid -> bottom`：`obstacle_game_core.sv:280`
- 用移动后的列检测碰撞：`obstacle_game_core.sv:296`

## 4. 车辆移动与碰撞判定

### Q10：车移动、障碍下降、碰撞判断是不是同一个时钟？

**答：**  
是同一个主时钟 `clk_i`。区别是：

- 车移动由 `key_pressed_i` 使能。
- 障碍下降由 `step_tick_i` 使能。
- 碰撞判断在同一个 `always_ff` 中使用本拍计算出来的 `next_car_col` 和 `next_bottom`。

这属于单时钟 + 多使能信号设计。

**代码位置：**

- 顶层把同一 `fpga_clk_i` 接给所有模块：`obstacle_car_top.sv:151`
- 车辆移动：`obstacle_game_core.sv:267`
- 障碍下降：`obstacle_game_core.sv:277`
- 碰撞检测：`obstacle_game_core.sv:293`

### Q11：为什么碰撞用 `next_car_col`，不用旧的 `car_col_o`？

**答：**  
这样可以让玩家在障碍下降同一拍按键时立即生效。逻辑顺序是：

1. 先根据按键算出移动后的 `next_car_col`。
2. 再根据 `step_tick_i` 算出下落后的 `next_bottom`。
3. 最后用 `next_bottom[next_car_col]` 判断碰撞。

如果用旧的 `car_col_o`，玩家明明在同一拍按键躲开了，仍可能按旧位置判定撞车，体验不合理。

**代码位置：**

- 先算移动后位置：`obstacle_game_core.sv:267`
- 再判断碰撞：`obstacle_game_core.sv:293`

### Q12：为什么同时按左右键时不移动？

**答：**  
这是为了避免输入冲突。代码只在左键按下且右键没按下时左移，或右键按下且左键没按下时右移。两个方向同时按下，不满足任一分支，因此保持原列。

**代码位置：**

- 左右键互斥判断：`obstacle_game_core.sv:271`
- testbench 覆盖同时按键不移动：`tb_obstacle_car.sv:570`

## 5. 按键、防抖与时基

### Q13：为什么需要按键防抖？

**答：**  
机械按键按下/松开瞬间会抖动，如果直接使用原始输入，可能一次按键触发多次移动。`key_debounce` 先做两级同步，再要求输入保持新状态达到 `DEBOUNCE_MS` 才确认变化。

确认从未按下变为按下时，输出 `key_pressed_o` 单周期脉冲；松开不会触发游戏动作。

**代码位置：**

- 两级同步：`key_debounce.sv:53`
- 计数确认稳定：`key_debounce.sv:80`
- 只在确认按下时产生脉冲：`key_debounce.sv:92`
- testbench 验证一次按下只产生一个脉冲：`tb_obstacle_car.sv:384`

### Q14：`tick_gen` 输出的 tick 是不是时钟？

**答：**  
不是。`tick_o` 是一个主时钟周期宽度的使能脉冲。所有模块仍在 `posedge clk_i` 工作，只是在 `if (tick_o)` 条件中执行低速动作。

**代码位置：**

- 模块说明：`tick_gen.sv:8`

## 6. 数码管与 LED 显示

### Q15：数码管如何显示 6 列 3 层游戏画面？

**答：**  
每个数码管代表一列。每列只用 A/G/D 三个横段表示三层：

- A 段：上层障碍。
- G 段：中层障碍。
- D 段：底层障碍和车。

`sevenseg_scan` 使用动态扫描，每次只选中一位数码管，快速轮询后人眼看到 6 位同时显示。

**代码位置：**

这是初始界面提示。IDLE 时障碍清空、车列保持在中间，通过 `blink_phase` 控制车位闪烁，提示玩家当前在初始等待状态，可以按任意键开始。

### Q17：生命值 LED 如何显示？

**答：**

3 -> 0111
2 -> 0011
1 -> 0001
0 -> 0000

剩余 LED 做呼吸灯。扣血时，被扣掉的 LED 会先爆闪一段时间，再保持熄灭。

**代码位置：**

## 7. 蜂鸣器与音乐播放

### Q18：为什么现在改成音符表，而不是 PCM ROM？

**答：**  
PCM ROM 更像原音频，但音乐数据太大，综合时间和片上存储压力都明显增加。现在的 `buzzer_note_player` 只保存“音符编号 + 节拍长度”，再用方波分频播放，资源占用小得多，也更符合无源蜂鸣器的常见播放方式。

代价是音质和伴奏会被简化，只保留主旋律。对这个小游戏来说，背景、胜利、失败三个提示音的识别度比原曲音质更重要。

**代码位置：**

- `buzzer_note_player` 模块说明：`buzzer_note_player.sv:3`
- 音符频率分频：`buzzer_note_player.sv:84`
- 音符/节拍表生成：`tools/generate_buzzer_note_player.py:192`

### Q19：无源蜂鸣器播放音乐的核心原理是什么？

**答：**  
无源蜂鸣器本身不会自动发固定音，需要 FPGA 输出周期性方波。不同音高对应不同频率，例如 523Hz 约等于 C5。代码里为每个音符保存频率，计算半周期计数：

```systemverilog
half_cycles = CLK_HZ / (note_hz * 2)
```

计数到半周期就翻转一次内部方波 `beep_raw`，于是得到对应频率。当前开发板蜂鸣器按低电平有效处理，模块最后通过 `BUZZER_ACTIVE_LOW` 把内部方波反相到 `beep_o`；节拍表决定这个音持续几个基本时间单位。

**代码位置：**

- 输出极性设置：`buzzer_note_player.sv:88`
- 半周期计算：`buzzer_note_player.sv:90`
- 音符持续时间：`buzzer_note_player.sv:124`
- `beep_raw` 翻转：`buzzer_note_player.sv:341`

### Q20：三首音乐分别是什么？

**答：**

- 背景音乐：进入 RUN 后循环播放 `See You Again` 主旋律背景曲。
- 胜利音乐：短促上行提示音，进入 WIN 后播放一次。
- 失败音乐：短促下行提示音，进入 LOSE 后播放一次。

这些旋律由 `tools/generate_buzzer_note_player.py` 维护，并生成试听 WAV 到 `music/note_player_preview/`。

**代码位置：**

- 背景旋律：`tools/generate_buzzer_note_player.py:133`
- 胜利旋律：`tools/generate_buzzer_note_player.py:144`
- 失败旋律：`tools/generate_buzzer_note_player.py:172`
- WAV 试听生成：`tools/generate_buzzer_note_player.py:483`

### Q21：为什么失败音乐里有 `E4/G4/A4` 这种绝对音名？

**答：**  
失败音效需要明显比胜利音更低、更沉。如果只用背景旋律那套简谱音级，音区不够直观，所以失败短曲额外使用少量绝对音高，保证它听起来是低音下行，而胜利音是高音上行。

**代码位置：**

- 绝对音高频率表：`tools/generate_buzzer_note_player.py:22`
- 失败旋律表：`tools/generate_buzzer_note_player.py:172`

### Q22：普通碰撞短音会不会影响胜利/失败音乐？

**答：**  
不会。RUN 状态有循环背景音乐，普通碰撞发生时播放器会临时进入 `MODE_COLLISION` 播 150ms 短音，短音结束后回到背景音乐。胜利/失败音乐只在进入 WIN/LOSE 结算状态时启动，不会被普通碰撞短音打断。

**代码位置：**

- 空闲态碰撞短音：`buzzer_note_player.sv:472`
- 碰撞短音输出：`buzzer_note_player.sv:483`

### Q23：胜利/失败音乐是完整播放吗？

**答：**  
是。`music_loop_o=0` 时播放一次，播到歌曲末尾后 `done_o` 拉高一拍并静音；状态机仍停在 WIN/LOSE，等待按键返回 IDLE。背景音乐使用 `music_loop_o=1`，在 RUN 状态循环播放。

**代码位置：**

- 胜利/失败启动时 `music_loop_pending=0`：`obstacle_game_core.sv:330`
- 背景启动时 `music_loop_pending=1`：`obstacle_game_core.sv:263`
- 曲末循环或 done：`buzzer_note_player.sv:1273`

### Q24：音乐修改后需要手动改 Verilog 吗？

**答：**  
不建议手动改生成后的长表。正确流程是修改 `tools/generate_buzzer_note_player.py` 里的旋律表，然后运行：

```bash
python tools/generate_buzzer_note_player.py
```

脚本会重新生成 `buzzer_note_player.sv` 和三份 WAV 试听，保证 RTL 与试听文件一致。

**代码位置：**

- 生成入口：`tools/generate_buzzer_note_player.py:496`

## 8. 资源与工程文件

### Q25：这块板子是不是存储资源很少？

**答：**  
板子外部存储不小，例如 SPI Flash / SD 卡，但最容易直接放进 RTL 里综合的片上 LUT/BRAM 资源有限。整首 PCM 音频如果直接进工程，会明显拖慢综合并占用大量存储。

当前使用音符表后，资源压力主要来自音符/节拍 case 表和方波分频器，远小于 PCM ROM。若后续要明显提升音质，可以改用 SPI Flash、SD 卡或 DDR 做流式读取，但这会增加外部存储控制器和文件读取逻辑，超出当前课程设计重点。

**代码位置：**

- 当前蜂鸣器源文件：`buzzer_note_player.sv:1`
- `.xpr` 中的 RTL 文件列表：`Obstacle_Avoidance_Car_Project.xpr:93`

### Q26：工程里为什么还保留生成脚本和试听 WAV？

**答：**  
生成脚本是音乐表的源头，便于以后换旋律或微调节奏。试听 WAV 是给人耳检查用的，能在重新综合前先判断旋律是否合适。真正参与综合的是 `buzzer_note_player.sv`。

如果只改了 WAV 而没有重新生成 SV，硬件声音不会变化；如果只手改 SV 而不改脚本，下次运行脚本会覆盖手改内容。

**代码位置：**

### Q28：如果老师问“这个能综合吗？”

## 10. 一句话答辩总结

本设计采用单时钟域结构，使用 tick enable 控制低速游戏逻辑。游戏核心用 FSM 管理 IDLE/RUN/WIN/LOSE，通过 LFSR 生成障碍，并用 `safe_col` 保证始终存在可达安全路径。显示部分用数码管动态扫描呈现 6 列 3 层画面，LED 用 PWM 表示生命值。蜂鸣器采用音符表、节拍表和方波分频器播放背景/胜利/失败旋律，资源占用小，适合单引脚无源蜂鸣器。
